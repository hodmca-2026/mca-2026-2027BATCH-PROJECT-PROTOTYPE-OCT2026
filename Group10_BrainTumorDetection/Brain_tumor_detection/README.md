# XAI & GenAI Based MRI Brain Tumor Detection Using CNN

A research/educational **medical imaging decision-support system** — not an autonomous
diagnostic tool. A doctor/researcher always reviews the AI output before it is finalized.

Workflow: **MRI Upload → Validation → Preprocessing → CNN Prediction → Confidence Score →
Grad-CAM Explanation → GenAI Draft Report → Doctor Review → Save Case History**

---

## 1. Research gap / motivation

Most published brain-tumor CNN classifiers optimize for accuracy in isolation and behave
as black boxes; explainability (e.g. Grad-CAM) is usually bolted on as a separate
visualization rather than integrated into a reviewable clinical artifact, and very few
systems connect prediction → explanation → a structured, human-reviewed report → case
history in one auditable workflow.

**This project's contribution:** it integrates CNN prediction, Grad-CAM explanation, and
an AI-assisted structured report into a single reviewable workflow with a human
(doctor/researcher) always in the loop — rather than treating classification accuracy as
the whole problem.

## 4. Database schema (summary)

`Role` → `User` → `Case` (patient_ref_id, no PII) → `MRIImage` → `Prediction`
(→ `ModelVersion`) → `Report`. `AuditLog` records every significant action
(login, upload, prediction, report generation/review) with user + timestamp.
See `backend/app/models/models.py` for full column/relationship definitions.

## 6. Local setup (no Docker)

### 6.1 Train the CNN (do this first)

```bash
cd ml
python -m venv venv
venv\Scripts\activate          # Windows
# source venv/bin/activate     # Mac/Linux
pip install -r requirements.txt
```

Download the [Brain Tumor MRI Dataset (Kaggle, Nickparvar)](https://www.kaggle.com/datasets/masoudnickparvar/brain-tumor-mri-dataset)
and extract it into `ml/dataset/` so you have `ml/dataset/Training/` and `ml/dataset/Testing/`,
each with `glioma/ meningioma/ notumor/ pituitary/` subfolders.

```bash
python explore_dataset.py       # sanity check
python train.py --epochs 15 --arch resnet18
```

This saves `ml/models/best_model.pth` and `ml/models/metrics.json`. **Until you run this,
the backend serves an explicitly-labeled untrained placeholder model** — the app still
works end-to-end, but predictions are not meaningful (see Section 8).

### 6.2 Backend

```bash
cd backend
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env          # Mac/Linux: cp .env.example .env
python seed_db.py               # creates roles + demo user doctor@example.com / Doctor@123
uvicorn app.main:app --reload
```

Backend runs at `http://localhost:8000`. Swagger docs at `/docs`.

### 6.3 Frontend

```bash
cd frontend
npm install
npm run dev
```

Frontend runs at `http://localhost:5173` and proxies `/api` calls to the backend.

Log in with `doctor@example.com` / `Doctor@123`.

## 7. Docker setup

```bash
docker compose up --build
```

- Backend: `http://localhost:8000`
- Frontend: `http://localhost:5173`

The `ml/` folder is mounted into the backend container so it can load a model you've
already trained (`ml/models/best_model.pth`). Train the model on your host machine first
(Section 6.1) — training inside the container is possible but not configured by default
since it needs the dataset mounted too and a GPU-enabled base image for practical speed.

**Switching to SQL Server**: uncomment the `sqlserver` service and the corresponding
`DATABASE_URL` in `docker-compose.yml`. The schema (`backend/app/models/models.py`) is
plain SQLAlchemy and needs no changes.

## 8. Model performance — honesty note

`ml/train.py` prints and saves **real** metrics (accuracy, precision, recall, F1,
confusion matrix, per-class sensitivity/specificity) computed on the held-out `Testing/`
split — no fabricated numbers. If you have not yet run training, `metrics.json` does not
exist and the dashboard/admin screens clearly show **"Untrained / Demo Placeholder"**
rather than pretending to have real accuracy.

**Known limitation**: the public Kaggle dataset has no patient IDs, so a strict
patient-level train/val/test split (avoiding the same patient's scans in both train and
test) is not possible here — this is disclosed rather than hidden, and is worth noting
explicitly in your report/viva as a limitation of any model trained on this dataset.

## 9. Testing plan

- **Unit-level**: validate `gradcam.py` produces a heatmap of the expected shape;
  validate upload endpoint rejects non-image files, oversized files, and files with a
  spoofed content-type (via `Image.verify()`).
- **Integration**: full flow test — create case → upload → predict → explain → generate
  report → review/approve → appears in case history.
- **Manual/UI**: exercise loading states, empty states (no cases yet), and error states
  (invalid file, expired session → redirected to login).
- **Model evaluation**: `train.py`'s held-out test-set metrics serve as the model's
  evaluation report — re-run after any dataset or architecture change.

## 10. Viva / defense notes

- Be ready to explain **why Grad-CAM, not a segmentation model**: Grad-CAM explains an
  existing classifier's decision without needing pixel-level tumor annotations, which the
  classification-only Kaggle dataset doesn't provide.
- Be ready to explain the **GenAI report's guardrails**: it only receives verified
  structured fields (case code, model output, disclaimer text) — never free-text patient
  history — and the system prompt explicitly forbids adding new medical facts. The output
  is always labeled a draft pending human review, and a doctor must approve it before its
  status changes.
- Be ready to explain the **SQLite-for-dev / SQL Server-for-production** choice: the
  spec asks for SQL Server (an enterprise, licensed database), which isn't practical to
  spin up for every grader/reviewer; the schema is portable and the swap is one
  environment variable.

## 11. Security & privacy notes

- Passwords hashed with bcrypt; JWT-based auth; role-based route protection
  (`require_role("admin")` etc.).
- Upload validation: content-type allow-list, size limit, and a real image-integrity
  check (`PIL.Image.verify()`) so a malicious file can't slip through disguised as a JPEG.
- `patient_ref_id` is an opaque reference the doctor/researcher supplies — the system
  never asks for or stores patient names, DOB, or other identifying data.
- Every significant action is written to `AuditLog` with the acting user and timestamp.

## 12. Disclaimer (shown throughout the UI)

> This system is a research/educational decision-support tool. It does not provide a
> medical diagnosis. The Grad-CAM heatmap indicates regions that influenced the model's
> prediction; it is not a confirmed tumor boundary. All AI-generated content requires
> review and approval by a qualified professional before any clinical use.

### Honest notes (important for the viva)
- **The symptom score is a rule-based indicator, not an ML prediction.** There is no patient dataset to train a
  symptom model honestly, so weights are simple, documented judgement values (`backend/app/routers/symptoms.py`).
  The UI and PDF say it is not a diagnosis and not clinically validated.
- **"Recommendations" are non-clinical next steps only** (consult a specialist, bring original scans, treat
  low-confidence results with caution). The system never suggests treatment or medication.
- **The doctor directory is DEMO data** (fictional names, placeholder phone numbers, flagged `is_demo`).
  Replace the entries in `backend/app/core/seed.py` with verified doctors before any real use.
- **Hindi/Marathi text is a first draft** — have a fluent speaker review the medical wording.
- The generated report text and PDF are in English.

## 14. Honest model evaluation (`ml/evaluate_model.py`)

The validation score printed while training comes from a random slice of `Training/`, which can contain
near-duplicates of training images, so it is optimistic. After training, run (from `ml/`, venv active):

```
python evaluate_model.py
```

It scores the saved model on the official `Testing/` folder, finds test images that are near-duplicates of a
training image (`dedup.py`) and re-scores **without** them (the leakage-controlled, headline result), then saves
`confusion_matrix.png`, `dedup_pairs.png` (a visual check of the flagged pairs) and updates `metrics.json`
(the original is kept as `metrics.v1.json`). The app's **Model & admin** page then shows the confusion matrix,
per-class sensitivity/specificity and the model card.

Other changes: Grad-CAM no longer leaks hooks between predictions and works on GPU; uploads that are colour
photos, blank or tiny images are rejected instead of being classified; a low-confidence banner is shown when the
top probability is below 70%.
